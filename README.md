# Agent Long Task Skill

> **让 AI 编码助手在长任务里不失忆、不烂尾的工作流技能。**
>
> 一句话原理：**AI 的记性只有一瞬，那就别让它记——把记忆放进硬盘。**

一个可直接装进 AI 编程助手（DeepSeek Harness / Claude Code 等支持 `SKILL.md` 的工具）的技能包。
当你上下文快满、要换窗口、怀疑 AI 忘了事、或者两个窗口改冲突了——调用它，它会先问清你的情况，再给你该发什么提示词。

---

## 你是不是遇到过这些

- 让 AI 改一个项目，聊到第 30 轮，它开始"忘记"前面说过的话，把你早就否决过的方案又提一遍
- 上下文满了换个新窗口，结果它像失忆一样，你得从头把项目背景讲一遍
- 任务做到一半，它说"已完成"，你一跑测试，全是红的
- 两个窗口同时改同一个项目，改完发现撞车了，谁也不敢动
- 本来三小时的活，做了两天，最后还是烂尾了

**这不是模型不够聪明，是方法用错了。**

这个仓库解决的就是这一件事：**怎么让 AI 在跨几十轮、跨多个窗口的长任务里，始终知道自己做到哪了。**

---

## 一、长任务为什么会烂尾（三个真实原因）

用大白话讲，就三件事：

**1. 上下文窗口是一张小桌子。**
活越干越多，桌子越堆越满。堆满了，新东西就没地方放——它开始丢旧东西。

**2. 丢了它不告诉你。**
它不会说"我忘了"。它会用"我觉得"把空白填上——于是开始编文件路径、编函数名、编"这个功能已经做完了"。
**这比直接承认忘了危险得多。**

**3. 换窗口等于换一个新人。**
新窗口真的是一张白纸，它看不到旧窗口的任何内容。你不讲，它就瞎猜；你讲，你就得每次都重讲一遍。

所以问题的本质不是"模型记性差"，而是：**你把记忆放在了最不该放的地方——对话里。**

---

## 二、为什么"扩大窗口"和"压缩记忆"都不管用

人们通常试三种办法，三种都不行：

### 办法一：RAG —— 每次干活前翻书

给 AI 一个知识库，每次动手前检索相关内容塞给它。

**为什么不行**：翻书能解决"这个接口怎么用"，解决不了"这面墙我刷到第几遍了"。
**书是知识，工地是状态。** 长任务需要的恰恰是状态。

更糟的是，检索是"猜哪个相关"——它可能翻到一页看起来很像、但实际不对的内容，然后基于错误前提开工。

### 办法二：会话压缩 —— 每干一段写张便签

把前面几十轮对话总结成一小段，腾出空间继续。

**为什么不行**：摘要一定会丢东西，而且丢的往往不是"刷了墙"这种大事，而是"这面墙用的是 A 牌底漆、第二遍要等 4 小时、业主说过这里不能打孔"这种硬约束。

而且它是**越压越糊**的：第三次压缩是在第二次压缩的产物上再压一遍。传话游戏玩三轮，全变样。

### 办法三：扩大窗口 —— 换一张更大的桌子

从 20 万 token 扩到 200 万。

**为什么不行**：

1. **桌子再大，总会满**。任务需要的信息量是随工作量增长的，窗口是个常数。临界点只是往后推了一点，问题的形状没变。
2. **崩溃了救不回来**。进程挂了、窗口关了，那 200 万 token 从来没存在硬盘上。
3. **每轮都要为全部历史付费**。40 轮任务，每轮带 200 万 token，就是 40 次 200 万的钱。
4. **太长了反而更糊涂**。上下文越长、越二手，模型对中间部分的注意力越差。

### 一张表总结

| 方法 | 本质 | 为什么崩 |
|---|---|---|
| RAG | 用检索替代记忆 | 把状态当知识查，概率召回保证不了正确 |
| 会话压缩 | 有损摘要 | 不可逆、丢硬约束、越压越糊 |
| 扩大窗口 | 加大常数 | 形状没变、崩溃不可恢复、成本翻倍、注意力稀释 |

**共同错误**：都在试图把「随任务增长的信息量」塞进「一个固定大小的窗口」。

**正确做法**：让信息根本不用进窗口。

## 三、核心思路：把大模型当 CPU 用

这是整套方法的出发点，只有一句话：

> **上下文窗口是寄存器，不是硬盘。**

| 计算机 | 这套方法里对应的东西 |
|---|---|
| CPU 寄存器（极小、极快） | 上下文窗口 |
| 内存 + 硬盘（大、持久） | 文件系统 + Git 仓库 |
| 程序计数器 / 栈 | 任务清单 + Git 提交记录 |
| 系统调用 / 读写磁盘 | shell 命令、文件读写、跑测试 |
| 进程重启 | 清空上下文、开新会话 |

由此推出三条原则：

### 原则一：环境即记忆

**真相源必须在窗口外面。**

任何只存在于对话里的决策，等于只存在于寄存器里——一次崩溃就没了。
所以决策必须立刻落盘：架构决策、接口约定、失败过的尝试及原因。

判断标准只有一句：**下一个空白窗口只读几个文件，能不能 5 分钟内正确接手？**

### 原则二：串行优于并行

**同一时刻，一个真相源，只能有一个写者。**

串行牺牲的是吞吐量，换来的是：

- **可归因**：出了问题，能定位到具体哪一次改动
- **可回滚**：一次改动一个提交，出问题精确撤回
- **可验证**：一次只验一个功能，成本是常数

并行省的是"等待时间"，赔的是"合并 + 调试 + 返工"。在多文件、有耦合的项目里，**通常赔得更多**。

（只读任务——调研、审查、写文档——可以随便并行，因为它们不写。）

### 原则三：测试驱动

**完成信号必须是外部的、确定性的、可增量的。**

为什么？因为"它说做完了"根本不算数。

- **外部**：判据在模型脑子外面。你问它"做完了吗"，它一定说做完了。
- **确定性**：同样输入必然同样输出。让另一个 AI 当裁判不行——它有偏好、会抖动。
- **可增量**：能单独验一个功能，不用每次跑全系统。

**机器可判定的最小信号是退出码**：`0` = 过，非 `0` = 不过。

## 四、双阶段架构是什么

把长任务在**时间上**切成两段，两段的成本结构完全不同。

### 阶段一 · 开荒（一次性，1~2 小时）

**产出的是"环境"，不是功能代码。**

想像你要装修一套房子：第一阶段不是砌墙，而是**出图、搭脚手架、定材料清单、定验收标准**。

产出这 7 样东西：

```
AGENTS.md          怎么构建、怎么测试、什么不许做
FEATURES.md        要做什么，每项可独立验收
PROGRESS.md        做到哪了、断在哪、下一步第一个动作
测试框架            能跑起来，有一个能通过的冒烟测试
全量检查命令        一条命令跑完 lint + 类型检查 + 测试
基线 commit         一个可以随时回滚的起点
prompts/resume.md   接手流程（让"新窗口第一步"固定下来）
```

**关键**：这一步不写任何功能代码。它的产品是"给未来的自己看的说明书"。

### 阶段二 · 循环（每轮 15~40 分钟，一轮一个功能）

```
读环境（5 个文件）
   ↓
取一个未完成的功能
   ↓
先写测试，确认它失败（红）
   ↓
写最少代码让它通过（绿）
   ↓
跑全量检查
   ↓
更新 PROGRESS.md → git commit → 清空上下文
```

**为什么这样能省 token**：

```
传统方式：第 n 轮的输入 = 前面全部 n-1 轮的历史   → 成本 O(n)
双阶段：  第 n 轮的输入 = 5 个文件 + 这一次的任务   → 成本 O(1)
```

40 轮的活，成本差 40 倍。

### 它凭什么解决问题

因为每一轮的输入是**固定的几个文件**，不是"全部历史"。

这一条直接推出四个结果：

- 成本不随任务变长而爆炸
- 任意时刻崩溃都能恢复
- 每一轮都能归因、回滚
- 上下文永远是新鲜的，不会腐烂

### 六个好处

| 好处 | 一句话 |
|---|---|
| 成本可控 | 40 轮任务，成本差 40 倍 |
| 可恢复 | 任意时刻崩溃，读 5 个文件就能接手 |
| 可归因 | 一轮一个功能一次提交，坏了知道怪哪轮 |
| 不腐化 | 每轮上下文都是新鲜的 |
| 人只做判断 | 你不用反复讲背景，只做"确认/拍板" |
| 知识变资产 | 项目知识沉在文件里，不随窗口消失 |

### 六条注意事项

1. **阶段一偷懒 = 阶段二十倍偿还**（失败案例第一大原因）
2. **环境文档过期比没有更糟**——AI 会基于错误状态高效地跑偏
3. **测试改弱 = 验收器失效**，禁止为通过测试而改测试
4. **同一工作区只能有一个写窗口**
5. **交接摘要永远"后发"**（先让新窗口独立观察，再拿摘要对账）
6. **验收标准必须人拍板**，AI 只负责起草

## 五、这个技能做什么

你调用它之后，它**不会直接甩一段模板给你**。它会：

```
第 0 步：问你三个问题（每个选项都带识别信号，防止你判错）
         ↓
         判定你属于 6 种情况中的哪一种
         ↓
         必须明说「你属于情况 X，因为……」，让你能当场纠正
         ↓
第 1 步：给你 2~4 步操作，每步配「可复制提示词 + 大白话为什么」
         ↓
第 2 步：给出本次最容易踩的坑
```

### 六种情况

| 情况 | 你什么时候会遇到 |
|---|---|
| **1 · 首次接管** | 接手一个从没整理过文档的老项目 |
| **2 · 常规推进** | 有环境了，正常做下一项 |
| **3 · 常规交接** | 窗口快满了，要换个窗口 |
| **4 · 半成品交接** | 功能做到一半，但要换窗口 |
| **5 · 新需求立项** | 想做的事不在清单里 |
| **6a · 并行冲突** | 两个窗口改撞车了 |
| **6b · 体检** | 怀疑它忘了 / 开始编东西 |

### 十二句提示词

技能里内置了 12 条可以直接复制粘贴的提示词：

| 编号 | 干什么用 |
|---|---|
| P1 | 旧窗口保命交接（**最重要的一条**：先把成果存下来，再做别的） |
| P1-轻量版 | 有环境时的快速交接（3~5 分钟） |
| P2 | 新窗口考古（只读，测绘现状） |
| P3 | 补建 5 个环境文件 |
| P4 | 以后每个新窗口的一句话开工 |
| P5 | 判断"收尾还是交接" |
| P6 | 半成品交接（断点五要素） |
| P7 | 新窗口续接半成品 |
| P8 | 需求转译（把模糊需求变成可验收的条目） |
| P9 | 交接摘要对账 |
| P10 | 体检 5 问（判断它是不是真的忘了） |
| P11 | 环境健康检查（防文档漂移） |
| P12 | 并行冲突仲裁 |

## 六、安装

### 方式一：手动复制（推荐）

1. 克隆或下载这个仓库
2. 把 `changrenwu/` 整个文件夹复制到你的技能目录：

```
Windows:  C:\Users\<你的用户名>\.dsh\skills\changrenwu\
macOS/Linux: ~/.dsh/skills/changrenwu/
```

3. 确认目录结构是这样：

```
~/.dsh/skills/changrenwu/
├── SKILL.md
└── references/
    └── 术语表.md
```

4. 重启会话，你的技能列表里就会出现 `changrenwu`

### 方式二：命令行

```bash
git clone https://github.com/182han/agent-long-task-skill.git /tmp/agent-long-task-skill
cp -r /tmp/agent-long-task-skill/changrenwu ~/.dsh/skills/
```

### 如果你用的是 Claude Code 或其他工具

`SKILL.md` 是通用格式（带 `name` / `description` 的 Markdown）。
把 `changrenwu/` 放到对应工具的 skills / commands 目录即可，或者直接把 `SKILL.md` 的内容作为自定义指令。

## 七、怎么用

### 触发

任选其一：

```
/changrenwu
```

或者直接描述你的处境，它也会被触发：

```
我这个窗口快满了，不知道怎么交接
新窗口接手一个老项目，但没整理过文档
两个窗口好像改冲突了
AI 好像忘了我前面说过的话
```

### 一次完整的走一遍（场景：老项目第一次整理）

**第 1 步 · 在旧窗口发 P1**

旧窗口上下文快满了，你让它做收尾：

```
上下文快满了，现在做收尾交接。不要再开始任何新工作，不要优化代码。

【第 1 步：保命】
1. git status，贴完整结果
2. 有未提交改动：git add -A && git commit -m "wip: checkpoint before context reset"

【第 2 步：留最小痕迹】
创建/覆盖 PROGRESS.md，只写 6 节...
```

> **为什么先保命不先审计**：旧窗口只剩最后一口气。审计要读几十个文件，这个过程本身就能把它撑爆。结果往往是审计做到一半窗口崩了，连做好的工作都没提交。

**第 2 步 · 关掉旧窗口，开新窗口发 P2（考古）**

```
你接手一个已存在但我没理清状态的项目。这一轮只读，禁止改任何业务代码。
任务不是回忆过去，是测绘现在。
1.【Git】...
2.【状态文件】...
...
```

> **为什么审计放新窗口**：新窗口是白纸，空间大，正好干重活。而且它没有旧窗口的偏见，能独立判断"文档说的和代码做的是不是一回事"。

**第 3 步 · 看完考古结果，让它补建**

```
根据测绘结果补建环境，写在仓库根目录：
1. AGENTS.md ...
2. FEATURES.md ...
...
```

**第 4 步 · 以后每个新窗口，只说一句话**

```
读 prompts/resume.md，按流程执行。先从第 0 步侦察开始，不要写代码。
```

**到这里，你的项目就算正式进入双阶段了。**
以后所有新窗口都用这一条，你不用再解释任何背景。

## 八、它第一次会问你什么

技能启动后会用一张卡片问你三个问题。**每个选项都带识别信号**，你只要对号入座：

**Q1 · 这个项目有「环境」吗？**
- 有：工作区里能找到 `AGENTS.md` / `PROGRESS.md` / `FEATURES.md` / `prompts/resume.md` 中至少 2 个
- 没有或不确定：只有零散笔记
- 只有手写交接文件：有 `PROJECT_STATE.md` 之类，但没有上面那套

**Q2 · 当前窗口手上有「做到一半的活」吗？**
- 有：某个功能改了一半、测试还红着
- 没有：手头的活已收尾
- 撞车了：两个窗口在改同一处

**Q3 · 你这次想干什么？**
- 换窗口 / 继续做 / 开新任务 / 救火

三个答案一组合，就能唯一确定你属于 6 种情况里的哪一种。

## 九、十个最常见的坑

1. **在快满的旧窗口做审计** → 窗口撑爆，成果没提交
2. **让 AI 自己定义验收标准** → 它会定义成最容易达成的那个版本
3. **交接摘要放在指令前面** → 锚定效应，后面的矛盾会被它主动"解释掉"
4. **攒着不提交** → 一次崩溃全没
5. **让撞车的两个窗口互相协商** → 越修越乱（它们都基于过期地图）
6. **用"你记得吗"判断它有没有忘** → 它会自信地编
7. **并行改有耦合的模块** → git 不报冲突，一跑测试全红
8. **改弱测试让它通过** → 唯一的验收器失效了
9. **环境文档过期不维护** → AI 基于错误状态高效跑偏
10. **一个工作区开两个写窗口** → 状态竞争

> **不要问"它还记得吗"，要问"这件事落盘了吗"。**
>

> 没落盘 → 它记着也是假的安全感，一次崩溃全没。
