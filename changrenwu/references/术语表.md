# 术语表 · Agent 长任务工作流

> 读不懂时先看「大白话」列，再回来看「准确解释」。
> 分组顺序：架构 → 记忆 → 失效 → 执行 → 验证 → 运维。

---

## 一、架构层

| 术语 | 准确解释 | 大白话 |
|---|---|---|
| **双阶段架构**（Dual-Phase Architecture） | 把长任务在时间上切成两个阶段：第一阶段一次性建立环境契约，第二阶段反复做增量循环。两阶段的成本结构完全不同——前者是一次性投资，后者是摊销。 | 先花两小时把工地布置好，之后每天来人只干一间房。 |
| **Initializer Agent**（初始化智能体） | 任务开始时一次性运行的 agent。产出不是功能代码，而是环境：项目骨架、文档、任务清单、测试框架、恢复协议。质量要求高，因为后面每个会话都要读它。 | 开荒队长。 |
| **Coding Agent**（编码智能体） | 在已建立的环境中循环工作的 agent。每轮：读环境 → 取一个功能 → 写测试 → 实现 → 验证 → 提交 → 清空上下文。 | 每天来的施工队长，换人不换工地。 |
| **Bootstrap**（引导阶段） | 同「阶段一」。指从零到"可循环工作"的那段准备期。 | 搭台子。 |
| **Incremental Loop**（增量循环） | 阶段二每轮固定动作的循环体。特征是：单功能、有验证、有提交、有清理。 | 一轮一道菜，出锅尝一口，记一笔，翻篇。 |
| **环境契约**（Environment Contract） | 一组让"任何新会话都能正确接手"的文件与约定：构建方式、测试命令、功能清单、进度状态、断点协议、禁止事项。 | 交接单 + 工地规范。 |

## 二、记忆层

| 术语 | 准确解释 | 大白话 |
|---|---|---|
| **上下文窗口**（Context Window） | 模型单次推理能看到的 token 上限，是个常数，且每次都按输入量计费。 | CPU 寄存器：能装的东西极少，但极快。 |
| **环境即记忆**（Environment as Memory） | 把跨轮次需要的信息固化到文件系统，而不是堆在对话历史里。让"记忆"变成可寻址、可版本控制、可审计的外部资源。 | 记忆不在脑子里，在硬盘上。 |
| **State Offloading**（状态外置） | 把决策所需的状态从上下文搬到外部存储的具体动作。 | 寄存器不够用就写内存，而不是把寄存器做大。 |
| **真相源**（Source of Truth） | 对某个事实唯一权威的载体。本方法里是「文件 + git」，不是「对话里它说过的话」。 | 以文件为准，不以它说的为准。 |
| **工作集**（Working Set） | 某一轮推理实际需要装进上下文的最小信息集合。设计目标是：让工作集大小与任务总长度无关。 | 这一趟要用的工具，不是整个工具箱。 |
| **可恢复性**（Recoverability） | 任意时刻中断后，新会话能通过有限步骤重建正确状态的性质。 | 断电重启还能接着干。 |
| **断点**（Checkpoint） | 可恢复所需的最小快照：做到哪、改了什么、测试什么状态、下一步第一个动作。 | 游戏存档。 |
| **基线**（Baseline） | 一个已知良好、可回滚的起点快照，通常是一个 commit。 | 存档点，出事就回这里。 |

## 三、失效层（传统方法为什么不行）

| 术语 | 准确解释 | 大白话 |
|---|---|---|
| **RAG**（检索增强生成） | 把外部文档切块、向量化、建索引；查询时检索最相关片段拼进 prompt。解决"模型不知道的事实"。 | 每次干活前翻书。 |
| **Compaction**（会话压缩） | 把历史对话摘要成更短文本以腾出窗口。有损且不可逆。 | 每干完一段写张便签，把前面的扔掉。 |
| **有损压缩**（Lossy Compression） | 无法还原原始信息的压缩。检索和摘要都属于此类。 | 复印件的复印件。 |
| **Context Rot**（上下文腐化） | 上下文越长、越二手，模型的有效注意力越差，输出质量下降。 | 信息堆太多反而变糊涂。 |
| **Lost in the Middle** | 模型对长上下文中间部分的利用率显著低于开头和结尾。 | 中间那段它基本没看见。 |
| **级联误差**（Cascading Error） | 多次压缩后，早期误差被后续摘要继承并放大。 | 传话游戏，传三轮全变样。 |
| **幻觉**（Hallucination） | 模型生成看似合理但实际不存在的内容（文件路径、函数名、commit）。 | 一本正经地编。 |
| **上下文污染** | 前面失败的尝试、无关讨论留在窗口里，持续干扰后续判断。 | 桌上堆满废纸，干活找不到东西。 |

## 四、执行层

| 术语 | 准确解释 | 大白话 |
|---|---|---|
| **WIP = 1**（Work In Progress = 1） | 同一时刻只允许一个进行中的工作项。 | 一次只端一道菜。 |
| **串行**（Serial Execution） | 一个写者、一次一个改动。牺牲吞吐换确定性。 | 排一队，一个一个来。 |
| **并行**（Parallel Execution） | 多个写者同时改。省等待时间，但引入合并、调试、返工成本。 | 五个灶同时开火。 |
| **状态竞争**（Race Condition） | 多个写者基于各自过期的状态视图并发修改，结果不可预测。 | 两个人同时改一张表，谁也不知道最后是什么。 |
| **可归因性**（Attributability） | 出问题时能定位到具体是哪一次改动引入的。 | 坏了知道该怪谁。 |
| **契约冻结**（Contract Freezing） | 并行开始前把接口签名、数据格式定死并提交，禁止单方面修改。 | 先定规矩再分头干。 |
| **写集**（Write Scope） | 一个任务允许修改的文件集合，必须显式声明。 | 划好你的地盘。 |
| **范围蔓延**（Scope Creep） | 任务执行中不断"顺手"扩大改动范围，破坏可归因性。 | 说好刷墙，顺手把地板也换了。 |
| **串行重放**（Serial Replay） | 冲突后，把一方的改动一次一个 commit 重放到另一方，每步验证。 | 一个个放，放一个验一个。 |

## 五、验证层

| 术语 | 准确解释 | 大白话 |
|---|---|---|
| **TDD**（测试驱动开发） | 先写失败的测试（红）→ 写最少实现让它通过（绿）→ 在测试保护下重构。 | 先定验收单，再施工。 |
| **Red-Green-Refactor** | TDD 的三步循环。 | 红→绿→整理。 |
| **外部验证器**（External Verifier） | 不依赖模型自我判断的检查机制：测试、类型检查、lint、CI。 | 不听它说，看机器判。 |
| **确定性**（Determinism） | 同样输入必然得到同样输出，没有抖动。 | 一是一，二是二。 |
| **退出码**（Exit Code） | 进程结束时返回的整数，0 = 成功，非 0 = 失败。机器可判定的最小信号。 | 机器的"点头/摇头"。 |
| **可判定**（Decidable） | 结果能用明确规则判为通过或不通过，不需要人来"感觉"。 | 能算出来的，不是猜出来的。 |
| **冒烟测试**（Smoke Test） | 最小的一组"能跑起来吗"的测试。 | 先点个火看看着不着。 |
| **机器可判定 / 需人判断** | 验收标准的两类：前者能写成断言，后者需要人的审美或偏好。 | 一个交给机器，一个交给你。 |

## 六、运维层

| 术语 | 准确解释 | 大白话 |
|---|---|---|
| **漂移**（Drift） | 环境文档与实际代码逐渐不一致。 | 地图过期了。 |
| **健康检查**（Health Check） | 定期核对文档、功能清单、命令与实际是否一致。 | 定期校准。 |
| **Inbox 机制** | 用 `prompts/inbox.md` 这类文件把"待立项需求"从旧窗口传给新窗口，替代人肉复制粘贴。 | 收件箱，谁都能往里放。 |
| **冻结**（Freeze） | 冲突处理第一步：所有写者停止写入。 | 全体停手。 |
| **交接摘要**（Handoff Summary） | 旧会话产出的短文本，只写文件装不下的信息（风险、失败方向、待拍板决策）。 | 一张便签，不是监控录像。 |
| **对账**（Reconciliation） | 拿摘要去和文件/git 逐条比对，标注有证据/无证据/有反证。 | 拿便签对账本。 |

## 七、最容易混的三对

**1. RAG ≠ 环境即记忆**
- RAG 检索的是**只读知识**，环境即记忆维护的是**可写状态**。
- 前者回答"这个 API 怎么用"，后者回答"这个 API 我改到第几行了"。
- 用 RAG 管状态，等于用搜索引擎做数据库事务。

**2. 压缩 ≠ 断点**
- 压缩是**销毁**信息换空间；断点是**挑选**信息存盘。
- 前者不可逆，后者可回放。
- 所以：压缩越做越糊，断点越做越清。

**3. 串行 vs 并行不是快慢之争**
- 串行牺牲**吞吐**换**可归因**。
- 并行省了等待，赔上合并、调试、返工。
- 有耦合的项目里，通常赔得更多。并行的成立条件是：写集不相交 + 接口冻结 + 各自可验证 + 串行合并。
